## 學習目標

讀完這一課，你應該能理解 SQL Injection 為什麼發生，以及「參數化查詢」如何把資料與指令清楚分開。

## 把資料混進指令的危險

應用程式常要執行「查詢某個使用者」這類 SQL。如果程式把使用者輸入直接拼進字串：

```text
name = 輸入的內容
sql  = "SELECT * FROM users WHERE name = '" + name + "'"
```

攻擊者輸入的引號就可能把「資料」變成「指令的一部分」，這叫 SQL Injection。攻擊者可能讀取其他資料表、修改或刪除資料。

## 參數化查詢

正確做法是先把查詢結構寫好，使用者輸入只當參數傳進去，由資料庫驅動程式負責處理：

```text
sql  = "SELECT * FROM users WHERE name = ?"
參數 = [使用者輸入]
```

這樣輸入裡即使有引號、分號，也會被當成「資料的值」，不會改變查詢結構。預備語句（prepared statements）與 ORM 的參數綁定，底層都是這個概念。

## 常見誤解

- 不是「有引號就會被攻擊」，關鍵是輸入有沒有被當成程式碼的一部分。
- 使用 ORM 不代表自動安全；動態拼接、原生 SQL 沒綁參數仍可能出問題。
- 過濾特定字元容易漏，參數化才是根本解。
- 最小權限的資料庫帳號能降低成功注入後的傷害。

## 今日重點整理

- 注入的根源是資料與指令混在一起。
- 參數化查詢把兩者分開。
- 字元過濾容易漏，不是根本解。
- ORM 仍要避免動態拼接。
- 資料庫帳號只需要最低必要權限。

## 延伸思考

看看你寫過或看過的程式，找出所有把使用者輸入直接接進 SQL 字串的地方。如果改用參數化，程式碼會變成什麼樣子？
